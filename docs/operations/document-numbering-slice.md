# Document numbering — canonical shared contract

> Source status: Phase 3 allocator foundation retained; Issue #497 Lane H updates identity and active-series ownership.
> Production deployment remains a separately gated operation.

## Purpose

Document numbering is a Shared-domain service that provides installation-scoped, concurrency-safe and idempotent business numbers. It owns number-series configuration, period counters and append-only allocation history. Business domains call the allocator and snapshot the returned number on their own documents.

## Lane H contract

For standard document types:

- the server owns the technical series identity; clients do not choose or edit the technical `code`;
- the administration UI exposes only the business configuration needed by the Owner: document type, display name, prefix, number template and reset cycle;
- at most one series may be active for the same `(installation_id, document_type)`;
- activating or creating an active series fails if another active series already exists; the system never silently switches the active series;
- to replace a locked format, the operator explicitly deactivates the current series and creates/activates the replacement;
- old series, counters and allocations remain intact and queryable after replacement.

The database is the final concurrency boundary through the partial unique index `document_number_series_one_active_type_unique`. Service checks provide a clear business error, but correctness does not depend on `SELECT`-then-`INSERT` timing.

### Standard technical namespaces

The server maps standard document types to an internal technical namespace. Current compatibility bases are:

```text
SALES_ORDER          -> SALES_ORDER
PURCHASE_ORDER       -> PURCHASE_ORDER
GOODS_RECEIPT        -> PURCHASE_RECEIPT
DELIVERY_ORDER       -> DELIVERY_ORDER
INVENTORY_TRANSFER   -> INVENTORY_TRANSFER
INVENTORY_ADJUSTMENT -> INVENTORY_ADJUSTMENT
CUSTOMER_RETURN      -> CUSTOMER_RETURN
SUPPLIER_RETURN      -> SUPPLIER_RETURN
CUSTOMER_PAYMENT     -> CUSTOMER_PAYMENT
SUPPLIER_PAYMENT     -> SUPPLIER_PAYMENT
CUSTOMER_REFUND      -> CUSTOMER_REFUND
GOODS_ISSUE          -> GOODS_ISSUE
INVOICE              -> INVOICE
```

New standard-series technical codes are generated by the server from the mapped namespace plus an internal suffix. This allows multiple historical/inactive series for one document type while preserving the existing installation-scoped code uniqueness.

Existing business services that still ask for historical fixed codes are resolved centrally to the current active series by document type. Domain services therefore do not need to own numbering configuration or know the generated technical code.

Non-standard/custom document types retain the lower-level API capability to supply a valid technical code; the standard administration flow does not expose that field.

## Migration 077 reconciliation

`077_document_numbering_active_series` reconciles legacy duplicate-active data before installing the unique active-series index.

For each `(installation_id, document_type)` with multiple active rows, it keeps one deterministic survivor using this order:

1. prefer the known canonical legacy code for that standard type;
2. then prefer the series with more immutable allocations;
3. then the earlier `created_at`;
4. then stable `id` ordering.

All other active rows are changed to inactive. No series, counter or allocation is deleted or rewritten. Allocation history remains append-only.

## Core allocator guarantees retained from Phase 3

- reset policies: `NONE`, `YEARLY`, `MONTHLY`;
- period counters are isolated (`ALL`, `YYYY`, `YYYY-MM`);
- backdated allocation uses the supplied document date;
- allocation serializes the exact series/period counter;
- same installation + series + idempotency key replays the same allocation;
- reuse of an idempotency key with different date/metadata is rejected;
- allocation history is append-only at API and PostgreSQL trigger levels;
- after the first allocation, formatting fields are locked;
- inactive series cannot allocate new numbers;
- rendered document numbers remain unique per installation.

## Template contract

Supported tokens:

```text
{PREFIX}
{YYYY}
{YY}
{MM}
{SEQ}
```

Rules:

- `{SEQ}` appears exactly once;
- unsupported tokens/braces are rejected;
- literals use uppercase ASCII letters, digits, `.`, `_`, `/`, `-`;
- sequence values are zero-padded to `sequence_width`;
- rendered output is limited to 160 characters;
- `YEARLY` requires a year token;
- `MONTHLY` requires both a year token and `{MM}`;
- `start_counter` must fit the configured width and leave room for the next counter.

Example:

```text
prefix: SO-
template: {PREFIX}{YYYY}{MM}-{SEQ}
width: 6
result: SO-202608-000001
```

## Data model

### `shared.document_number_series`

Installation-scoped configuration, lifecycle and internal identity. Lane H adds the invariant of at most one active row per installation/document type.

### `shared.document_number_counters`

One mutable counter per installation + series + period. Counter state is allocator state, not a business document.

### `shared.document_number_allocations`

Append-only allocation history containing series, idempotency key, document date, period, counter, rendered number, actor, request, source app and metadata.

## API contract

```text
GET    /api/document-number-series
POST   /api/document-number-series
GET    /api/document-number-series/:id
PATCH  /api/document-number-series/:id
GET    /api/document-number-series/:id/allocations
POST   /api/document-number-series/:id/allocate
```

POST mutations require `Idempotency-Key`. PATCH requires `expectedUpdatedAt`.

For a standard document type, `POST /api/document-number-series` does not trust a client-supplied technical code. The server generates it. Creating/activating another active series of the same type returns `ACTIVE_SERIES_EXISTS` as a business conflict.

## Authorization and audit

- reads require `core.document-number.read`;
- configuration mutation and allocation require `core.document-number.write`;
- every query is installation scoped;
- first-time series changes and allocations write transactional audit records;
- replay returns the original allocation without consuming another counter or duplicating audit;
- public errors remain sanitized;
- browser traffic uses same-origin server-only gateways.

## Administration UI

Canonical route: `/document-numbering`, labelled `Số chứng từ`.

The standard workspace supports:

- list/filter series without presenting technical code as a business identity;
- create/edit document type, name, prefix, number structure and cycle;
- activate/deactivate explicitly;
- clear conflict copy when another series of the type is already active;
- format-lock state;
- test/reference allocation;
- immutable allocation history.
