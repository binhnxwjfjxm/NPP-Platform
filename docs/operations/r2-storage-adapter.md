# R2 Storage Adapter Foundation

## Purpose

This runbook describes the backend-only Cloudflare R2 adapter foundation for `npp-core/api`. The adapter is private by default, uses the S3-compatible AWS SDK v3, and does not make a provider request unless `R2_ENABLED=true` with complete server-side configuration.

This document does not confirm that a production bucket, credential, retention policy, backup, CORS policy, or lifecycle rule has been configured or verified.

## Backend configuration

Only server-side variables are supported:

```text
R2_ENABLED=false
R2_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
R2_REGION=auto
R2_BUCKET=<bucket-name>
R2_ACCESS_KEY_ID=<server-only>
R2_SECRET_ACCESS_KEY=<server-only>
R2_PUBLIC_BASE_URL=<optional>
R2_PRESIGNED_URL_MAX_SECONDS=900
R2_MAX_OBJECT_BYTES=<safe-limit>
R2_CONTRACT_ROUTE_ENABLED=false
```

No R2 credential may use a `NEXT_PUBLIC_` prefix. When `R2_ENABLED=true`, missing endpoint, bucket, access key, or secret key causes startup configuration to fail closed. Sanitized runtime config exposes only enabled/configured flags and numeric limits; it does not expose credentials, endpoint, bucket name, or public URL.

## Private-by-default adapter

`npp-core/api/src/storage/r2-adapter.js` exposes:

- `putObject(...)`
- `headObject(...)`
- `getObject(...)`
- `deleteObject(...)`
- `createPresignedGetUrl(...)`

Objects are not uploaded with public-read access. The adapter accepts only the configured bucket and installation-scoped object keys. Provider responses are reduced to stable fields rather than returned raw.

### Upload

Uploads accept a `Buffer`, `Uint8Array`, or readable stream plus an explicit content length. Known length is validated before the provider call and rejected when it exceeds `R2_MAX_OBJECT_BYTES`. Metadata is limited to safe string keys and values; secret-shaped keys or values are discarded. SHA-256 is calculated for in-memory bodies or validated when supplied.

### Download and metadata

`getObject` returns the provider body/stream with content type, length, metadata, checksum, and normalized ETag. It does not convert large bodies into text. `headObject` returns the same safe metadata subset without downloading the object.

### Delete

`deleteObject` validates installation scope and is idempotent when the provider reports that the object does not exist. Bulk deletion is not part of this foundation.

### Presigned GET

Presigned URLs are GET-only. TTL must be an integer from 1 through `R2_PRESIGNED_URL_MAX_SECONDS`. Download filenames are sanitized before use in content disposition. Signed URLs must never be written to logs, audit records, or error details.

## Object-key convention

Keys are generated by the server:

```text
<installation-id>/<namespace>/<yyyy>/<mm>/<uuid>-<safe-filename>
```

The installation ID comes from server-owned request context. Namespace is checked against an allowlist. Filenames reject slashes, backslashes, null bytes, traversal components, and unsafe length. A UUID prevents filenames from becoming unique identifiers.

Client-supplied `x-installation-id`, `x-actor-id`, `x-source-app`, raw bucket names, or complete object keys are not trusted.

## Protected contract route

The foundation verification route is:

```text
POST /api/storage/r2-test
```

It is hidden unless `R2_CONTRACT_ROUTE_ENABLED=true`, requires authentication, and requires permission:

```text
core.storage.r2.test.write
```

The route accepts only a small textual test payload, creates the object key server-side, uploads it, calls `headObject`, writes one audit record, and deletes the test object. The route uses the existing idempotency foundation; replay of the same `Idempotency-Key` and payload does not execute a second upload, while a different payload with the same key returns conflict.

No outbox event is created because this foundation has no storage event consumer.

## Audit consistency boundary

R2 mutation and PostgreSQL audit cannot share one atomic transaction. The contract operation therefore uses this sequence:

1. upload the object;
2. verify metadata with `headObject`;
3. write one audit record using server-owned request context;
4. delete the temporary contract object.

When upload succeeds but audit fails, the service performs a best-effort compensating delete and returns `STORAGE_AUDIT_FAILED`. If compensating cleanup also fails, it returns `STORAGE_AUDIT_CLEANUP_FAILED`. Audit data contains only key, content type, size, result, and adapter name—not file content, credentials, provider responses, or signed URLs.

## Error contract

Stable codes include:

```text
STORAGE_DISABLED
STORAGE_CONFIGURATION_INVALID
STORAGE_KEY_INVALID
STORAGE_OBJECT_TOO_LARGE
STORAGE_OBJECT_NOT_FOUND
STORAGE_UPLOAD_FAILED
STORAGE_DOWNLOAD_FAILED
STORAGE_DELETE_FAILED
STORAGE_PRESIGN_FAILED
STORAGE_PROVIDER_UNAVAILABLE
STORAGE_AUDIT_FAILED
STORAGE_AUDIT_CLEANUP_FAILED
```

Validation failures are not retryable. Appropriate provider availability failures are retryable. Raw provider messages, stacks, credentials, database-like URLs, and signed URLs are not exposed.

## Verification

Run:

```bash
npm --workspace npp-core-api run test
npm --workspace npp-core-web run typecheck
npm run verify
```

Unit tests inject the S3 client, presigner, storage contract operation, clock, and UUID. They do not call Cloudflare or require provider credentials. No external R2 smoke test is run by CI.

## Production readiness gate

Production enablement remains blocked until all of the following are separately verified:

- credentials are provisioned with least privilege;
- bucket policy is audited and remains private by default;
- CORS requirements are reviewed separately;
- lifecycle and retention behavior are explicitly decided;
- backup and retention are not assumed to exist;
- a non-production provider smoke test succeeds with isolated keys;
- size limits and allowed namespaces are approved;
- observability and alerting are approved;
- compensating-cleanup failures have an operational response;
- deployment and configuration changes receive accountable approval.

This foundation does not deploy, call, upload to, delete from, or reconfigure the production R2 bucket.
